# sol-workspace

Standalone **systems ontology toolkit** — a self-contained copy of the
`semantics`, `resolution`, and `shrapnel` schemas with all nexus-specific
plumbing removed, served by a small REST API.

## Layout

```
sol-workspace/
├── nexus-three-schemas.sql   # pg_dump of semantics/resolution/shrapnel from nexus (schema only)
├── sol-schema.sql            # transformed DDL for the sol database (generated by transform.py)
├── transform.py              # strips nexus-only tables/FKs/functions from the dump
├── seed.sh                   # reference seeds (e.g. shrapnel.field_type)
├── systemd/sol-api.service   # user unit — starts the API on boot
├── sol_api/                  # FastAPI service
│   ├── main.py               # schema-driven REST surface (semantics/resolution/shrapnel)
│   ├── db.py                 # shared asyncpg pool
│   ├── shrapnel.py           # shrapnel value-family encode/decode (Python port of TS shrapnel-srv)
│   └── routes/
│       ├── shrapnel.py       # /api/shrapnel/* domain routes
│       └── evaluate.py       # /api/evaluate/* SOLScript evaluation routes
├── API.md                    # frontend-facing REST reference (all calls + envelopes)
├── typespec/                 # TypeSpec contract for the API surface
│   ├── main.tsp              #   entry (service, server, imports)
│   ├── models.tsp            #   request/response models
│   ├── operations.tsp        #   all routes (gateway + shrapnel + evaluate)
│   └── tspconfig.yaml        #   emits OpenAPI 3.1 (npm ci + npx tsp compile)
├── client/                   # typed TypeScript client (generated from the contract)
│   ├── src/schema.d.ts       #   openapi-typescript output (generated — don't edit)
│   ├── src/wrappers.ts       #   one typed fn per endpoint (throws SolApiError)
│   └── smoke.ts              #   live smoke test (npx tsx smoke.ts)
├── pyproject.toml            # SOLScript wired in via [tool.uv.sources] path dep (editable)
└── .venv/
```

## Database

- Host database: `nexus` (untouched — sol is a copy, not a modification).
- New database: `sol` (PostgreSQL, owner `pguser`), containing only the
  three schemas above with nexus-only tables removed.

### What was removed vs. nexus

- **Tables dropped:** the full candidate/work-request pipeline, including
  its source-chunk and edge tables:
  `candidate`, `candidate_segment_set`, `candidate_source_chunk`, `harvest`,
  `implementation_plan`, `requirement`, `requirement_segment_set`,
  `owning_subsystem` (resolution + semantics), `specification`,
  `specification_lineage`, `work_request`, `work_request_edge`.
- **Dropped the 9 ontology tables duplicated in both semantics and
  resolution** (`canonical_asset`, `concept`, `concept_relationship`,
  `consumer_operation`, `execution_claim`, `identity_strategy`,
  `representation`, `representation_identity`, `representation_relationship`)
  — semantics was the original first take; resolution is the redeveloped
  reasoning layer, so the semantics copies are inert. `semantics` now keeps
  only its facts/provenance tables: `asset_identity_claim`, `asset_relation`,
  `asset_revision`, `drift_finding`, `evidence_item`, `evidence_type`,
  `relationship_type`, `snapshot`, `snapshot_observation`, `source_observation`,
  `source_observation_embeddings`, `statement_evidence`.
- **FKs dropped:** any constraint referencing the excluded tables
  (e.g. `representation.owning_subsystem_id`,
  `asset_identity_claim`/`asset_relation`/`asset_revision` → `canonical_asset`,
  `snapshot_observation` → `representation`).
- **Functions dropped:** `admit_and_record` (writes `peb.*`),
  `ensure_registered_service_asset` / `ensure_registered_work_request_asset`
  (write `registry.*` / `nebula.*`), their trigger functions, the three
  `owning_subsystem` CRUD functions, and the 27 `add_`/`update_`/`soft_delete_`
  CRUD helpers for the duplicated semantics ontology tables.
- **`check_statement_id` rewritten:** the `statement_evidence` trigger no
  longer validates `nebula.*`/`conduit.*` statement types (agent_record,
  work_request, implementation_plan, harvest_candidate) and its
  `concept_relationship` / `representation_relationship` / `execution_claim`
  branches now check `resolution.*` (the semantics copies are gone); the
  `statement_evidence_type_check` CHECK constraint is trimmed to match.

**Result:** 77 base tables + 1 view (`resolution.v_t24_execution_evidence`)
— 43 resolution, 12 semantics (facts/provenance only), 22 shrapnel.

### Regenerate sol from nexus (idempotent)

```bash
cd sol-workspace
PGPASSWORD=pgpass pg_dump -h localhost -U pguser -d nexus --schema-only \
  --schema=semantics --schema=resolution --schema=shrapnel \
  -f nexus-three-schemas.sql
python3 transform.py          # writes sol-schema.sql

PGPASSWORD=pgpass psql -h localhost -U pguser -d postgres -c "DROP DATABASE IF EXISTS sol;"
PGPASSWORD=pgpass psql -h localhost -U pguser -d postgres -c "CREATE DATABASE sol OWNER pguser;"
PGPASSWORD=pgpass psql -h localhost -U pguser -d sol \
  -c "CREATE EXTENSION IF NOT EXISTS vector; CREATE EXTENSION IF NOT EXISTS pg_trgm;
      CREATE EXTENSION IF NOT EXISTS citext; CREATE EXTENSION IF NOT EXISTS pgcrypto;
      CREATE EXTENSION IF NOT EXISTS btree_gist;"
PGPASSWORD=pgpass psql -h localhost -U pguser -d sol -v ON_ERROR_STOP=1 -f sol-schema.sql
```

## REST API

**Frontend-facing contract:** [`API.md`](API.md) — every endpoint, request
envelope, and response envelope with examples, verified against the live
service. The TypeSpec contract below is the machine-readable source of
truth that this document mirrors.

**Typed client:** [`client/`](client/) is a ready-to-use TypeScript
package generated from the compiled contract — `openapi-typescript` types
+ `openapi-fetch` runtime, with one typed wrapper per endpoint
(`health()`, `encode()`, `checkEntity()`, …). Types regenerate via
`npm run generate` when the contract changes. See `client/README.md`.

```bash
cd sol-workspace
.venv/bin/uvicorn sol_api.main:app --port 8111 --host 0.0.0.0
```

### systemd (runs on boot)

The API ships as a **user** unit (`systemd/sol-api.service`, linger enabled on
this host). Install:

```bash
cp systemd/sol-api.service ~/.config/systemd/user/
systemctl --user daemon-reload
systemctl --user enable --now sol-api.service
systemctl --user status sol-api.service
```

Logs: `journalctl --user -u sol-api -f`. The unit uses
`Restart=on-failure` and a hardening profile matching the repo's other
user services. It replaces any manually-detached `uvicorn` process on
:8111.

| Route | Purpose |
|-------|---------|
| `GET /health` | liveness + db check |
| `GET /api/schemas` | schemas and their tables |
| `GET /api/{schema}/{table}` | list rows (`page`, `per_page`, `?col=value` filters) |
| `GET /api/{schema}/{table}/{pk}` | fetch by primary key |
| `POST /api/{schema}/{table}` | insert (JSON body) |
| `PUT /api/{schema}/{table}/{pk}` | update by primary key |
| `DELETE /api/{schema}/{table}/{pk}` | delete by primary key |
| `GET/POST /api/shrapnel/*` | shrapnel domain routes (field-types, fields, objects, encode) |
| `GET /api/evaluate/status` | SOLScript interpreter load status |
| `POST /api/evaluate/refresh` | reload the interpreter from the database |
| `POST /api/evaluate/proposition/{id}` | evaluate a proposition (optional frame `context`) |
| `POST /api/evaluate/reason` | deterministic/hybrid reasoning over an entity |
| `POST /api/evaluate/check-entity` | per-rule invariant checks for an entity |

### Shrapnel value family (`/api/shrapnel/*`)

The `shrapnel` schema spreads one logical value across a base row
(`value` + `value_type_code`) plus typed extension tables (`value_long`,
`value_string`, …). The generic table gateway would return `{id,
value_type_code}` and leave the payload ambiguous — these domain routes
resolve it: `POST /api/shrapnel/encode` writes the base + extension rows in
one transaction, and object reads decode the right extension via a CASE on
the type code.

```bash
curl -s -X POST http://localhost:8111/api/shrapnel/encode -H 'Content-Type: application/json' \
  -d '{"values": {"name": "titanium-host", "cores": 16, "active": true, "meta": {"env": "prod"}}}'
# → {object_id, fields, decoded: {name: ..., cores: 16, active: true, meta: {...}}}
```

### Evaluation (`/api/evaluate/*`)

These call SOLScript's interpreter live (see below) against the `sol`
database. The interpreter is loaded lazily on first use and cached;
`POST /api/evaluate/refresh` rebuilds it from current DB state.

```bash
curl -s http://localhost:8111/api/evaluate/status
curl -s -X POST http://localhost:8111/api/evaluate/check-entity \
  -H 'Content-Type: application/json' -d '{"entity_id": "<uuid>"}'
```

## SOLScript — included by path, not copied

`sol-workspace/pyproject.toml` declares SOLScript as a **uv path source**,
so the toolkit imports the live package from `../nexus/python/SOLScript`
with zero duplication:

```toml
[project]
dependencies = ["solscript", ...]

[tool.uv.sources]
solscript = { path = "../nexus/python/SOLScript", editable = true }
```

`uv sync` (or `uv pip install -e ../nexus/python/SOLScript`) links it;
edits to the SOLScript source are picked up immediately. The evaluate
routes use `DatabaseLoader` + `ResolutionInterpreter` from that package.

> **Note:** the two `shrapnel` modules are deliberately distinct —
> `sol_api/shrapnel.py` is the Python port of the TS encode/decode lib,
> `sol_api/routes/shrapnel.py` is the HTTP router. No copy of SOLScript is
> involved anywhere.

## Tests

The suite runs against a dedicated `sol_test` database (created from
`sol-schema.sql` + seeds, dropped afterwards) — the real `sol` database is
never touched.

```bash
uv pip install pytest httpx   # once
.venv/bin/python -m pytest    # 34 tests, ~24s
```

Coverage:

- `tests/test_shrapnel.py` — field-type registry, field CRUD/upsert, and the
  encode → decode round-trip across all seven value types (Long/String/Double/
  Boolean/Timestamp/JSONB/UUID), including error cases (unknown type, 404s).
- `tests/test_evaluate.py` — interpreter status/refresh, proposition
  evaluation (Asserted), per-rule invariant checks (pass/fail/404), and
  deterministic/hybrid reasoning against a seeded Host concept chain.

## SOLScript portability

`nexus/python/SOLScript` loads from the DB via `DatabaseLoader`, which
queries only `resolution.*` and `shrapnel.*` tables (never `nebula.*`,
`vision.*`, etc.) and skips non-`resolution` schemas in `load_entities`.
Those tables exist identically in `sol`, so the loader works against both
databases — only the DSN differs:

```bash
# against nexus:
DSN="postgresql://pguser:pgpass@localhost:5432/nexus"

# against sol:
DSN="postgresql://pguser:pgpass@localhost:5432/sol"
```

Verified: running SOLScript's smoke test with the DSN pointed at `sol`
loads cleanly (all queries resolve; 0 rows until sol is populated).

### SOLScript fixes made during the port

Two latent bugs in `nexus/python/SOLScript` were fixed while wiring the
API (they affect nexus too — any comparison rule against a stored literal):

- **`expression_compiler.py`:** literals are stored as text in the schema
  (`'0'` with `return_type='integer'`), but the compiler returned them
  raw, so `cores > 0` failed with `TypeError: '>' not supported between
  instances of 'int' and 'str'`. `_coerce_literal` now coerces per
  `return_type` at compile time (integer/numeric/boolean; others pass
  through). All 151 SOLScript tests still pass.
- **`database_loader.py` (assessment):** `expression_operand.position` is
  1-based; a 0-based row crashes `load_expressions` with `IndexError`. No
  code change needed — the convention is enforced by the existing data
  (nexus uses 1-based positions throughout).
